Zeitreihensystem — Dokumentation

Performantes Zeitreihensystem für die Verwaltung von über 10 Millionen Zeitreihen. Gebaut auf TimescaleDB (PostgreSQL-Extension) mit Spring Boot Backend und React Frontend. Das System dient der Erfassung, Verwaltung und Analyse von Zeitreihendaten in verschiedenen Zeitdimensionen (15 Minuten bis Jahr).

Kernfähigkeiten

  • Zeitreihen-Management — Lesen, Schreiben, Löschen von Zeitreihen in 5 Zeitdimensionen (15min, 1h, Tag, Monat, Jahr)
  • On-the-fly Aggregation — Summierung beliebig vieler Zeitreihen mit Cross-Dimension- und Unit-Konvertierung
  • Stammdaten — Geschäftspartner, Währungen, Objekte, Einheiten
  • Batchplanung — Quartz-basiertes Job-System mit Cron/Intervall-Schedules und Ausführungshistorie
  • Berechtigungssystem — RBAC mit Keycloak-Integration, Gruppen, Feld-Restriktionen
  • Diagramme — Interaktive Charts mit Zoom, Downsampling, mehrere Bibliotheken zur Auswahl
  • Tab-basierte Navigation — Multi-Tab-Oberfläche mit Session-Persistenz (überlebt Browser-Refresh)

Dualer Persistenz-Ansatz

Das System verwendet zwei komplementäre Persistenz-Strategien, je nach Anwendungsfall:

  • Raw JDBC für alle Übersichtsabfragen — Performance-kritische Abfragen werden über die QueryRegistry gesteuert und liefern ein generisches TableResponse-Format. Alle Tabellen mit vielen Zeilen laufen über diesen Weg.
  • JPA/Hibernate für Einzel-CRUD-Operationen — findById, create, update, delete nutzen JPA-Repositories mit Entity-Mapping für Komfort und Typsicherheit.
  • Regel: findAll() oder Tabellen mit vielen Zeilen verwenden immer Raw JDBC, niemals JPA.
  • JPA-Konfiguration: ddl-auto=validate (Schema wird nicht automatisch geändert), open-in-view=false (keine Lazy-Loading-Probleme in Controllern).

Tabellendesign

  • ts_header — Metadaten jeder Zeitreihe (Key, Dimension, Einheit, Währung, Objekt-Zuordnung)
  • ts_values_* — Separate Werte-Tabellen pro Dimension mit unterschiedlichen Chunk-Größen
  • ts_object / ts_object_type — Übergeordnete Objekte mit 1:n Beziehung zu Zeitreihen
  • Stammdaten-Tabellen — ts_currency, business_partner, contact_person, batch_schedule
  • Auth-Tabellen — ts_auth_user, ts_auth_group, ts_auth_permission, ts_auth_field_restriction, ts_auth_resource
  • System-Tabellen — ts_query (SQL-Registry), filter_preset (gespeicherte Filter)

TimescaleDB-Features

  • Hypertables — Automatische Partitionierung nach Zeit für 15min, 1h, Tag, Monat
  • Hash-Partitionierung — Auf ts_id für schnellen Einzelreihen-Zugriff
  • Kompression — segmentby = ts_id, automatisch nach 3–6 Monaten
  • Stored Procedures — ts_sum_15min, ts_sum_1h für DB-seitige Summierung (PL/pgSQL)
  • Index — (ts_id, ts_time) für schnelles Lesen einzelner Zeitreihen

Backend-Patterns

Overview-Pattern (Übersichtsseiten)

Alle tabellarischen Übersichtsseiten folgen demselben Pattern: Raw JDBC über QueryRegistry für maximale Performance.

Controller (GET oder POST /query) │ ▼ OverviewRepository (Raw JDBC) │ ├── QueryRegistry.get("key") → SQL laden │ ├── FilterQueryBuilder.build(conditions, allowedColumns) → WHERE-Klausel │ └── PreparedStatement → ResultSet → List<Map<String, Object>> │ ▼ TableResponse { columns: ColumnMeta[], data: Map[] }

QueryRegistry + QueryLoader

  • QueryLoader parst XML-Dateien aus classpath:queries/*.xml beim Start (ApplicationReadyEvent)
  • Upsert in Tabelle ts_query (key, name, sql_text)
  • QueryRegistry lädt alle Queries aus DB in ConcurrentHashMap (@PostConstruct)
  • Neue Queries hinzufügen: XML-Datei in src/main/resources/queries/ anlegen

FilterQueryBuilder

  • Baut sichere WHERE-Klauseln aus FilterCondition-Objekten
  • Whitelist (allowedColumns) verhindert SQL-Injection
  • Werte werden parametrisiert (? Platzhalter)
  • Unterstützte Operatoren: =, !=, <, >, >=, <=, LIKE (case-insensitive), IN, BETWEEN, IS NULL, IS NOT NULL
  • Max. Wertlänge: 1000 Zeichen

TableResponse

  • Generische Antwort: List<ColumnMeta> + List<Map<String, Object>>
  • ColumnMeta: key (interner Name), label (Anzeigename), sqlColumn (SQL-Ausdruck), type (TEXT/NUMBER/DATE)

Detail-Pattern (Einzel-CRUD)

Stammdaten-Entitäten nutzen JPA/Hibernate für Einzeloperationen. Der Flow ist immer gleich:

Controller (POST/PUT/DELETE) │ ▼ Service (@Service, @Transactional) │ ├── Validierung (required fields, uniqueness) │ ├── DTO → Entity Mapping │ └── JpaRepository.save() / .delete() │ ▼ DTO Response (Entity → DTO Mapping)
  • Validierung im Service, nicht im Controller
  • DTO-Mapping: toDto() und toEntity() Methoden im Service
  • @Transactional auf Klassen- oder Methodenebene
  • @OneToMany Cascade: Service-Loop (clear + addAll), nicht JPA orphanRemoval
  • JpaRepository mit existsByField() für Uniqueness-Checks

Tab-System

Die Anwendung nutzt kein URL-basiertes Routing, sondern ein eigenes Tab-System (ähnlich wie eine IDE). Tabs werden in sessionStorage gespeichert und überleben Browser-Refresh (F5).

  • openTab(type, params?) — Neuen Tab öffnen (oder fokussieren bei Singleton)
  • closeTab(id) — Tab schließen (mit Close-Guard bei ungespeicherten Änderungen)
  • updateTabLabel(id, label) — Tab-Titel dynamisch ändern
  • getTabParams(tabId) — Parameter auslesen (z.B. entityId, mode)
  • registerCloseGuard(tabId, guard) — Warnung bei unsaved changes
  • Singleton-Tabs: Dashboard, Zeitreihen-Übersicht etc. — nur eine Instanz
  • Persistenz: sessionStorage (Key: "market-tabs"), überlebt F5, nicht Browser-Neustart

Security-Modell

Übersicht

Das System nutzt Keycloak als Identity Provider mit OAuth2/OIDC. Die Autorisierung erfolgt über ein eigenes 3-Ebenen-RBAC-Modell (Users → Groups → Permissions), das in der lokalen Datenbank gespeichert wird.

Keycloak (Identity Provider) │ JWT Token ▼ Spring Security (SecurityConfig) │ Bearer Token Validation ▼ UserRegistrationFilter │ Auto-Registrierung bei erstem Login ▼ PermissionService │ Effektive Berechtigungen berechnen ▼ AuthUser → AuthGroup → AuthPermission (Resource × ObjectType → Read/Write/Delete)

RBAC-Modell

  • AuthUser — Wird automatisch beim ersten Keycloak-Login angelegt (UserRegistrationFilter)
  • AuthGroup — Benutzer können mehreren Gruppen zugeordnet werden
  • AuthPermission — Pro Gruppe: Resource + ObjectType → canRead / canWrite / canDelete
  • AuthFieldRestriction — Feld-Level-Einschränkungen pro Gruppe (z.B. "Preis" nur für bestimmte Gruppen sichtbar)
  • AuthResource — Definiert verfügbare Ressourcen (z.B. "zeitreihen", "business-partners")

Permission-Aggregation

Aspekt Logik Erklärung
Read/Write/DeleteOR über GruppenWenn EINE Gruppe das Recht hat → Benutzer hat es
Field-RestrictionsAND über GruppenNur wenn ALLE Gruppen einschränken → Feld ist eingeschränkt
AdminBypassAdmin überspringt alle Checks

Frontend-Integration

Der AuthContext stellt Berechtigungsprüfungen als React-Hooks bereit:

  • canRead(resourceKey, objectTypeId?) — Leseberechtigung prüfen
  • canWrite(resourceKey, objectTypeId?) — Schreibberechtigung prüfen
  • canDelete(resourceKey, objectTypeId?) — Löschberechtigung prüfen
  • isFieldRestricted(resourceKey, fieldKey, objectTypeId?) — Feld-Restriktion prüfen
  • isAdmin — Admin-Status
  • Sidebar: Admin-Nodes nur für Admins sichtbar, andere Nodes nach ResourceKey gefiltert

Zeitreihen-Editor

Der Zeitreihen-Editor ist die zentrale Arbeitsmaske. Er unterstützt das Laden mehrerer Zeitreihen gleichzeitig, inline Bearbeitung, Zeitraumwahl und Diagramm-Ansicht.

  • Zeitraumwahl — Start/Ende Datepicker, automatisch aus Laufzeit der Zeitreihe(n) vorbelegt
  • Multi-Zeitreihen — Mehrere Zeitreihen mit unterschiedlichen Laufzeiten werden nebeneinander angezeigt. Fehlende Datenpunkte werden mit NaN aufgefüllt (kein Fehler)
  • Inline-Editing — Werte direkt in der Tabelle bearbeiten. Geänderte Zellen werden farblich hervorgehoben (Amber)
  • Dirty-Tracking — Ungespeicherte Änderungen werden verfolgt. Close-Guard warnt vor Datenverlust
  • Speichern — Schreibt geänderte Tage parallel zum Backend (ein Request pro geändertem Tag pro Zeitreihe)
  • Footer-Statistiken — Min, Max, Avg, Sum für jede Spalte in der Tabelle

Werte-Tabelle

Die Werte-Tabelle (ValuesTable) ist eine virtualisierte, inline-editierbare Tabelle. Für 15min-Zeitreihen zeigt sie bis zu 96 Werte pro Tag, für Stunden-Zeitreihen 24.

DST-Bewusstsein: Am Tag der Zeitumstellung zeigt die Tabelle 92 (Sommerzeit) bzw. 100 (Winterzeit) Viertelstundenwerte an. Die Timestamps werden korrekt berechnet.

Use Case: Aggregation (Summierung)

Auslösung

In der Zeitreihen-Übersicht können mehrere Zeitreihen ausgewählt und über die Kontextaktion "Summieren" aggregiert werden.

Ablauf

Mehrfachauswahl in Übersicht │ ▼ POST /api/timeseries/aggregate { tsIds: [1, 2, 3], start: "2024-01-01", end: "2024-12-31" } │ ├── Gleiche Dimension + Einheit? │ └── Ja → SQL-Shortcut (Stored Procedure ts_sum_*) │ ├── Verschiedene Dimensionen? │ └── Disaggregation auf kleinste gemeinsame Dimension │ ├── Verschiedene Einheiten? │ └── Automatische Unit-Konvertierung │ └── Parallele Reads (ExecutorService, 10 Threads) │ ▼ Synthetische Summen-Zeitreihe im Editor (read-only)

Cross-Dimension-Aggregation

Wenn Zeitreihen unterschiedliche Dimensionen haben (z.B. 15min + Tag), werden alle auf die kleinste gemeinsame Dimension disaggregiert. Beispiel: Ein Tageswert wird auf 96 Viertelstundenwerte aufgeteilt.

Performance-Optimierungen

  • SQL-Shortcut — Bei gleicher Dimension + Einheit: Stored Procedures (ts_sum_15min, ts_sum_1h) summieren komplett in der Datenbank
  • Parallele Reads — Dedizierter ExecutorService (nicht ForkJoinPool!), 10 Threads
  • Bulk-Header — HeaderRepository.findByIds() statt N Einzelabfragen
  • ANY(array) vermeiden — Parallele Einzelabfragen sind schneller als ANY(array) bei Hypertables mit Hash-Partitionierung

Use Case: Batchplanung

Konzept

Das Batch-System basiert auf dem Template→Instanz-Muster: Job-Typen werden im Code definiert (AbstractBatchJob), Planungen (Schedules) in der Datenbank. Pro Job-Typ können beliebig viele Schedules angelegt werden.

Code (AbstractBatchJob) Datenbank (batch_schedule) ┌──────────────────────┐ ┌─────────────────────────┐ │ CleanupOrphanedHeaders│ ◄──── │ Schedule 1: täglich 02:00│ │ Job │ │ Schedule 2: manuell │ │ - getJobKey() │ │ Schedule 3: alle 6h │ │ - getParameters() │ └─────────────────────────┘ │ - execute(params) │ └──────────────────────┘

Job-Katalog

Der Endpoint GET /api/batch-jobs/catalog liefert alle verfügbaren Job-Typen mit ihren Parameterdefinitionen. Jeder Parameter hat einen Typ (STRING, INTEGER, BOOLEAN, DATE, ENUM, PATTERN), ob er Pflicht ist, und einen Defaultwert.

Schedule anlegen

  • Job-Typ wählen — Dropdown mit verfügbaren Jobs aus dem Katalog
  • Schedule-Typ: NONE (nur manuell), CRON (Cron-Ausdruck), INTERVAL (Sekunden)
  • Parameter — Dynamisches Formular basierend auf den Parameterdefinitionen des Job-Typs
  • Aktivierung — Schedule wird sofort in Quartz registriert

Manuell auslösen

Über den Button 'Jetzt ausführen' kann ein Schedule manuell getriggert werden. Optional können Parameter überschrieben werden.

Historie

  • Alle Ausführungen mit Status (RUNNING, COMPLETED, FAILED)
  • Startzeit, Endzeit, Dauer
  • Anzahl bearbeiteter Datensätze
  • Logfile-Einsicht (text/plain)
  • Filterbar nach Schedule, Status, Zeitraum

Use Case: Benutzerverwaltung (Admin)

Nur für Administratoren. Die Admin-Seiten sind nur sichtbar, wenn der angemeldete Benutzer Admin-Rechte hat.

Benutzer

  • Liste — Alle registrierten Benutzer (aus lokaler DB, synchronisiert mit Keycloak)
  • Anlegen — Benutzer in Keycloak erstellen (Benutzername, E-Mail, Passwort)
  • Admin-Flag — Admin-Status setzen/entfernen (mit Lockout-Schutz: letzter Admin kann sich nicht selbst entfernen)
  • Aktivieren/Deaktivieren — Benutzer in Keycloak sperren
  • Passwort setzen — Passwort in Keycloak zurücksetzen
  • Effektive Berechtigungen — Anzeige aller berechneten Rechte eines Benutzers

Gruppen

  • Liste — Alle Gruppen mit Mitgliederzahl
  • Anlegen/Bearbeiten — Name, Beschreibung
  • Mitglieder — Benutzer hinzufügen/entfernen
  • Berechtigungen — Pro Ressource und optional pro Objekttyp: Read/Write/Delete

Berechtigungs-Matrix

Die Berechtigungs-Matrix zeigt alle Gruppen als Spalten und alle Ressourcen als Zeilen. Für jede Kombination können Read (R), Write (W) und Delete (D) Rechte gesetzt werden.

Feld-Restriktionen

Zusätzlich zu den CRUD-Rechten können pro Gruppe Feld-Restriktionen definiert werden. Diese schränken die Sichtbarkeit einzelner Felder ein (z.B. 'Preis' nur für bestimmte Gruppen).

Use Case: Sidebar-Navigation

Aufbau

Die Sidebar wird aus einer XML-Konfiguration (sidebar.xml) generiert und bietet eine hierarchische Baumnavigation.

Daten/ ├─ Dashboard └─ Zeitreihen Stammdaten/ ├─ Geschäftspartner ├─ Objekte ├─ Objekttypen ├─ Einheiten └─ Währungen System/ ├─ Batchplanung/ │ ├─ Planungen │ └─ Historie └─ Einstellungen Administration/ ← nur für Admins ├─ Benutzer ├─ Gruppen └─ Berechtigungen

Berechtigungs-Filterung

  • Admin-Nodes (Administration/*) sind nur für Admins sichtbar
  • Andere Nodes werden nach ResourceKey gefiltert (nur sichtbar, wenn Benutzer Leserecht hat)
  • Fallback auf Frontend-Default, wenn Backend-API nicht erreichbar

Konfiguration

Die Sidebar-Struktur wird in src/main/resources/sidebar.xml definiert. Änderungen erfordern einen Backend-Neustart. Das Frontend hat einen Fallback in sidebarTree.ts, der manuell synchron gehalten werden muss.

Use Case: Filter-System

FilterBuilder

Jede OverviewPage hat einen integrierten FilterBuilder, der über den 'Filter'-Button in der Toolbar geöffnet wird.

  • Bedingungen — Spalte + Operator + Wert (mehrstufig)
  • Operatoren — =, !=, <, >, >=, <=, LIKE, IN, BETWEEN, IS NULL, IS NOT NULL
  • SQL-Preview — Zeigt die generierte WHERE-Klausel an
  • Sichere Ausführung — Whitelist für Spalten, parametrisierte Werte, Max. 1000 Zeichen pro Wert

Filter-Presets

  • Speichern — Aktuelle Filterbedingungen als Preset speichern (Name + Bedingungen)
  • Laden — Gespeichertes Preset anwenden
  • Default — Ein Preset pro Seite als Default markieren (wird beim Öffnen automatisch angewendet)
  • Scopes — USER (nur für eigenen Benutzer) oder GLOBAL (für alle, nur Admins)
  • Löschen — Eigene Presets oder GLOBAL-Presets (nur Admins)

Technische Details

Filter werden über POST /query mit einem FilterRequest (Liste von FilterCondition-Objekten) an das Backend gesendet. Der FilterQueryBuilder validiert die Spalten gegen eine Whitelist und erzeugt parametrisierte SQL-WHERE-Klauseln.
